# 阿里云盘企业版同步接入验证 实施指导 v1

## 任务目标

建立一条**基于现有阿里云盘企业版订阅**的、可验证且可复现的文件访问链路，为后续开发自用的 Android + Ubuntu 文件同步 App 打基础。

长期目标是让 Android 手机和 Ubuntu 电脑能够通过云端中转，同步一个可视为 Obsidian Vault 的目录树（Markdown、附件、子目录以及必要的 `.obsidian` 内容等）。

当前阶段**不是实现完整同步引擎**，而是先回答并验证一个关键问题：

> 现有的阿里云盘企业版 + 企业版 API Key，是否能够作为自研同步 App 的可用云端文件后端；如果可以，官方支持的接入边界和调用方式是什么？

必须明确：**当前没有购买、开通或计划依赖 PDS 开发者版订阅。** 本任务应优先使用现有阿里云盘企业版能力完成验证。文档、CLI 或 Skill 名称中出现 `PDS`、`aliyun pds`、`PDS Skill`，不等于当前账号拥有或需要 PDS 开发者版；这是阿里企业网盘相关底层工具/能力的命名。

## 背景与上下文

当前已完成的阿里云盘企业版初始化如下：

- 企业/组织名称：`Chenthre Cloud`
- 当前使用者：`chenthre`
- `chenthre` 同时是超级管理员和普通用户主体
- 已存在企业空间：`Chenthre Cloud`，界面显示容量 `10.00 GB`
- 已创建独立团队空间：`Sync`，界面显示容量 `5.00 GB`
- 企业版的 Beta API Key 功能已开启
- 已由 `chenthre` 创建一个 API Key
- 该 API Key 当前权限模式选择的是：**保持与登录用户的空间与权限一致**
- API Key 的实际密钥值属于敏感信息，不应写入本文档、代码仓库、日志、聊天内容或截图

企业版当前对 API Key 的官方定位是：外部 Agent 可通过 PDS Skill 获得企业网盘文件读写能力。当前需要进一步验证的是，这种凭证能否以官方支持的方式被本地程序/CLI/SDK复用，并最终适合作为自研同步 App 的后端。

## 需求与约束

### 硬性要求

1. **后端前提**
   - 当前只有阿里云盘企业版订阅。
   - 不得把“PDS 开发者版”写成当前依赖、已有资源或既定方案。
   - 可以使用阿里官方面向企业网盘发布的 `PDS Skill`、`aliyun pds` 插件等工具，因为这是企业版当前官方文档中支持的接入路径之一。

2. **测试隔离**
   - 所有写入、覆盖、重命名、移动和删除测试只能发生在团队空间 `Sync` 内。
   - 建议使用独立测试目录，例如：

     ```text
     Sync/_chenthre_sync_probe/
     ```

   - 不得对 `Chenthre Cloud` 企业空间中的现有内容执行破坏性操作。

3. **密钥安全**
   - 不把 `uk-...` API Key 写入仓库中的源码、Markdown、shell history 示例、测试 fixture 或普通日志。
   - 优先通过交互式官方配置、环境变量、受限权限的本地配置文件或系统密钥存储保存凭证。
   - 若必须创建本地 `.env` 或凭证文件，确保其在 `.gitignore` 中，并限制文件权限。
   - 输出调试信息时必须脱敏。

4. **当前 API Key 权限较宽**
   - 当前 Key 设置为“保持与登录用户的空间与权限一致”，而该用户是超级管理员。
   - 因此当前验证阶段必须格外限制操作范围。
   - 验证成功后，后续生产/开发使用建议换成“自定义”权限，只授权 `Sync` 空间的必要读写能力。

5. **以官方支持为准**
   - 优先使用阿里官方帮助文档和本机 `--help` 输出确认参数，不要猜 CLI 参数名。
   - 不得以 PDS 开发者版 OpenAPI 文档中基于 RAM AccessKey 的调用方式，直接推导“企业版 `uk-...` API Key 可以同样调用”。
   - 如果企业版 API Key 的直接 HTTP/SDK 支持没有明确依据，则结论必须写成“未确认”。

6. **Beta 风险**
   - 当前企业版 API Key 功能处于 Beta / 公测阶段，且当前标注限时免费。
   - 后续正式 App 设计必须把“接口、计费、权限模型未来可能变化”视为外部依赖风险。

### 偏好或建议

- 优先先用 CLI 完成最小冒烟验证，再决定是否编写 Dart/Python/其他语言的探针。
- 测试文件使用纯文本或 Markdown，例如 `hello.md`，内容应易于 hash/字节比较。
- 记录文件操作返回的稳定标识，例如 `file_id`、`revision_id`；这些字段未来可能用于同步状态判断。
- 如果覆盖写确实产生新 revision，应记录实际行为和相关字段，但本阶段不实现版本历史逻辑。
- 验证成功后，建议创建用途专用的 API Key，并限制到 `Sync` 空间，遵循最小权限原则。

## 实施思路

### 阶段 1：检查并建立官方 CLI 工具链

优先验证阿里官方企业网盘文档当前推荐的 CLI/插件组合。

官方文档当前给出的最低版本要求为：

- 阿里云 CLI `>= 3.3.16`
- PDS 插件 `>= 0.7.7`

可先执行：

```bash
aliyun version
aliyun pds version
aliyun pds --help
aliyun pds config --help
```

如果尚未安装或版本过旧，可按官方当前文档安装/升级，例如：

```bash
curl -fsSL https://aliyuncli.alicdn.com/setup.sh | bash
aliyun configure set --auto-plugin-install true
aliyun plugin update
aliyun pds version
```

不要在实施指导中硬编码未知的 API Key 配置参数；以本机 `aliyun pds config --help` 和官方文档为准。

### 阶段 2：配置企业版 API Key

目标是让 `aliyun pds` 使用认证类型：

```text
api_key
```

如果出现类似：

```text
pds profile default domain not found
```

则需要确认并配置企业的 `domain_id`。官方文档当前示例提示可通过：

```text
aliyun pds config --domain-id <id> ...
```

但其余参数仍以本机帮助信息为准，不要推测。

注意：`domain_id` 在官方企业网盘相关文档中用于表示域/实例标识；本任务中实际值目前尚未确认。

### 阶段 3：只读验证

先进行不改变云端数据的验证：

1. 验证认证成功。
2. 查询当前用户可访问的空间。
3. 找到名称为 `Sync` 的团队空间。
4. 记录其 `drive_id`（若返回）。
5. 记录企业/域的 `domain_id`（若返回）。
6. 验证能列出 `Sync` 根目录内容。

如果查询“所有空间”出现权限类 `403`，不要立即判定 API Key 失效；官方文档提到部分域级列举权限不足时，工具可能需要分别查询个人/团队/企业空间。以实际错误和工具行为为准。

### 阶段 4：受限 CRUD 冒烟测试

在 `Sync` 下创建专用测试目录，例如：

```text
/_chenthre_sync_probe/
```

执行以下流程：

1. 创建测试目录。
2. 本地创建 `hello.md`，例如：

   ```markdown
   # Chenthre Sync Probe

   Hello from Ubuntu.
   ```

3. 上传到测试目录。
4. 查询并记录远端文件元数据，若有则记录 `file_id`、大小、修改时间、revision 信息。
5. 下载为另一个本地文件。
6. 使用 `sha256sum` 或等价方式比较上传前和下载后的字节一致性。
7. 修改本地 `hello.md`，执行覆盖写。
8. 验证远端内容确实更新；若可见 revision，记录覆盖前后 revision 变化。
9. 重命名该文件。
10. 若工具明确支持且权限允许，执行一次目录内移动测试。
11. 删除本次测试文件。
12. 删除本次创建的空测试目录。

所有删除操作必须明确指定测试目录中的本次创建对象，禁止使用模糊批量删除。

### 阶段 5：确认“自研 App 可调用性”边界

这是本阶段最关键的技术调查之一。

需要区分以下三种路径：

```text
A. API Key -> PDS Skill -> 企业网盘
B. API Key -> aliyun pds 官方插件/CLI -> 企业网盘
C. API Key -> 自研程序的官方 REST/SDK -> 企业网盘
```

A 已被企业版官方文档明确描述；B 需要本地实际验证；C 目前仍是待确认事项。

执行 Agent 应：

- 查阅阿里云企业版 API Key 官方文档和官方企业网盘 Skill 文档。
- 检查 `aliyun pds` 帮助、配置及可用子命令。
- 如果官方文档明确提供 API Key 对应的 REST/SDK 认证规范，则按该规范做一个最小程序验证。
- 如果只有开发者版 OpenAPI 文档要求 RAM AccessKey/SDK，不得将其当作企业版 `uk-...` API Key 的直接调用依据。
- 如果只能确认 CLI/Skill 可用，则本阶段结论应明确写成“企业版 API Key 已验证可通过官方 CLI/Skill访问；直接 App REST/SDK 接入仍未确认”。

可以检查官方 CLI/插件本身暴露的公开命令能力以评估未来是否可被本地同步服务包装调用，但不要依赖网页抓包或未公开的私有接口。

## 关键决策

1. **当前云端优先使用阿里云盘企业版。**
   - 这是已有订阅，先验证其能力，不因为工具名包含 PDS 就迁移到 PDS 开发者版。

2. **单独使用 `Sync` 团队空间作为同步沙盒。**
   - 目的在于隔离开发测试与其他企业空间内容。

3. **先验证后实现。**
   - 在云端 CRUD、认证方式和自动化边界未验证前，不开始设计完整同步引擎。

4. **不依赖私有 Web 接口。**
   - 网页或官方 App 内部接口即使可以抓包，也不作为长期自用 App 的正式依赖。

5. **当前 API Key 仅用于开发验证。**
   - 当前 Key 权限跟随超级管理员用户，范围过宽。
   - 后续真正接入同步 App 时应优先改为最小权限的 `Sync` 专用 Key。

## 边界情况

实施时重点注意：

- `aliyun pds` 插件名中出现 PDS，并不代表需要 PDS 开发者版订阅。
- `domain_id` 未配置时，可能出现 profile/domain 相关错误；不要把它误判为 API Key 无效。
- 查询所有空间的 `403` 可能是域级列举权限问题，需要继续测试具体团队空间访问能力。
- 移动文件可能因为接口/路由权限单独报 `403 CheckRouterAccessFailed`；需要记录为具体能力限制，而不是笼统判定整个 API 不可用。
- API Key 当前继承超级管理员权限，任何误操作影响面较大。
- API Key 为 Beta 功能，未来可能改变计费、能力或认证形式。
- 开发者版 OpenAPI 使用的 AccessKey/签名流程和企业版 `uk-...` API Key 不是同一件事，不得混用结论。
- 如果 CLI 可以完成上传下载，但无法通过公开 API 直接调用，仍然不能据此宣称 Android App 可以直接使用同样的 HTTP 接口。
